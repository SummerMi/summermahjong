# ADR-0002：对局状态持久化选型（内存 / SQLAlchemy 双实现）

- 状态：已采纳
- 日期：2026-11-02
- 决策者：工程 D「持久化分支」
- 相关文件：`app/services/repository/`、`app/services/store.py`、`app/core/config.py`、`app/main.py`、`tests/test_persistence.py`

---

## 1. 背景

改造前的对局状态只存在进程内存里（`app/services/store.py` 的 `GameStore`）：

- 优点：零依赖、启动即用，适合 demo 与 CI（121 个测试不用起数据库）；
- 硬伤：进程一重启对局全丢，多实例部署时各实例各存一份，无法做「多端同时看一局」。

目标岗位（广深后端实习）的 JD 里 MySQL 出现 5 次、Redis 4 次，所以仓库需要一条**真实的
持久化分支**，同时**不能破坏默认零依赖的演示路径**，也不能改路由层与现有测试。

## 2. 决策一：接口优先 + 两个实现（依赖倒置）

新增抽象 `GameRepository`（`app/services/repository/base.py`），只定义四个协程：

```python
class GameRepository(ABC):
    async def create(self, seed: int | None = None) -> GameState: ...
    async def get(self, game_id: str) -> GameState: ...
    async def discard(self, game_id: str, seat: str, tile: str) -> GameState: ...
    async def clear(self) -> None: ...
```

- `GameStore`（内存）与 `SqlGameRepository`（SQLAlchemy 2.0 异步）都实现它；
- 路由依赖 `StoreDep = Annotated[GameRepository, Depends(get_store)]`，
  `lifespan` 按 `settings.database_url` 决定把哪一个挂到 `app.state.store`；
- **路由层零改动**：`app/api/routes/games.py` 一行没动，也不知道背后是字典还是 MySQL 表。

配套地，把「发牌」和「打牌」的规则逻辑抽成纯函数
（`new_game_state` / `apply_discard`），两个实现共用同一份：

> 存储层只负责「怎么存取」，不负责「规则是什么」。

这样不会出现「换库就换行为」的经典事故，测试也能直接断言
「相同 seed 在内存实现和 SQL 实现下发出同一副牌」。

**为什么不选「路由里 if 判断」**：那是把存储细节泄漏到 API 层，每加一种存储就要改所有路由，
也无法给测试注入假实现。接口 + 依赖注入是这里唯一正确的形态。

## 3. 决策二：SQLite 验证、MySQL 生产，只改 URL

代码里没有任何方言分支（除了 SQLite 没有行锁那一处），DSN 由 `DATABASE_URL` 注入：

| 环境 | DSN | 用途 |
|---|---|---|
| 默认 | 空字符串 | 纯内存，零依赖，demo / CI |
| 本地验证 | `sqlite+aiosqlite:///./games.db` | 真实落库、重启可查，不需要装 MySQL |
| 生产 | `mysql+aiomysql://user:pass@host:3306/mahjong` | 多实例共享状态 |

技术选型：**SQLAlchemy 2.0 异步（`AsyncEngine` + `aiosqlite` / `aiomysql`）**，理由：

1. FastAPI 是 async 栈，用同步驱动会阻塞 event loop（或把每个请求丢线程池），异步驱动与
   现有 `async def` 服务层一致；
2. 2.0 的 `Mapped[...]` 声明式模型 + `select()` 风格类型友好，也顺便展示对新 API 的掌握；
3. 换 MySQL 只改 DSN，ORM 代码不动（MySQL 驱动 `aiomysql` 另装，演示环境用不到）。

本地不连真 MySQL 的原因：本机 MySQL 5.7 没有可用账号密码，且 SQLite 与 MySQL 的差异
（行锁、JSON 类型、时区）都已在代码/注释里显式处理，见下文。

启动时 `Base.metadata.create_all()` 建表（幂等），关闭时 `engine.dispose()` 释放连接池。
**关闭时不删数据**（内存实现才 `clear()`），这正是「重启后 game_id 仍可查」的前提。

## 4. 决策三：JSON 列 vs 拆表

`games` 表结构：

```sql
CREATE TABLE games (
    game_id        VARCHAR(32) PRIMARY KEY,   -- uuid4().hex
    seed           INTEGER        NULL,       -- 复盘用；可空
    wall           JSON           NOT NULL,   -- 剩余牌墙（字符串数组）
    hands          JSON           NOT NULL,   -- {"east": [...], ...}
    discards       JSON           NOT NULL,   -- {"east": [...], ...}
    current_player VARCHAR(8)     NOT NULL,
    created_at     DATETIME       NOT NULL,
    last_access    FLOAT          NOT NULL,   -- 闲置 TTL 清理
    version        INTEGER        NOT NULL   -- 乐观锁版本号
);
```

**取舍：JSON 列胜出**（对当前模型）：

- 对局状态是典型的**聚合根**：一次请求完整读、完整写，永远不查询「某个座位手里有哪些牌」；
- 拆成 `game_tiles(game_id, seat, zone, tile, position)` 后，一次读要 N+1 行、一次打牌要
  `DELETE + INSERT` 多行，事务范围变大、延迟变高，收益只在「按牌检索」场景才出现；
- SQLite（3.9+）与 MySQL 5.7+ 都支持 JSON，MySQL 里还是原生 `JSON` 类型（可校验格式）。

**代价（面试要主动说）**：JSON 列不能建普通索引做「按牌查询」/统计分析；
`JSON` 整体读写有序列化开销；MySQL 会重排 JSON 对象的 key（数组顺序保留，所以牌墙/手牌
顺序不受影响）。真要做「牌谱分析、胜率统计」时，应再拆出
`discard_events(game_id, seq, seat, tile, created_at)` 这类**事件表**（CQRS 的读模型），
而不是把聚合根拆散——写入路径保持简单，分析走旁路。

**时区**：SQLite / MySQL 的 `DATETIME` 都不保存时区，统一按 UTC 写入；
读回 naive 值时在 `_row_to_state` 里补 `tzinfo=UTC`，保证响应里的 `created_at`
始终是带时区的 ISO 8601（与内存实现的 `datetime.now(UTC)` 对齐）。

## 5. 决策四：乐观锁 vs 悲观锁（打牌原子性）

一次打牌是「读状态 → 校验 → 改三处（手牌/牌河/牌墙）→ 写回」的复合操作，必须防止两个并发
请求交叉执行导致「一张牌被打出两次」或「手牌凭空多一张」。

实现（`SqlGameRepository.discard`）：

```python
async with self._engine.begin() as conn:          # 一个事务
    stmt = select(GameRow).where(GameRow.game_id == game_id)
    if conn.dialect.name != "sqlite":
        stmt = stmt.with_for_update()             # MySQL/PG：悲观行锁，串行化同一局
    row = (await conn.execute(stmt)).mappings().one_or_none()
    ...
    result = await conn.execute(
        update(GameRow)
        .where(GameRow.game_id == game_id, GameRow.version == state.version)  # 乐观锁 CAS
        .values(..., version=state.version + 1)
    )
    if result.rowcount != 1:
        raise ConcurrentUpdateError(game_id)      # 409 GAME_CONFLICT，让客户端重试
```

**两层保护，各司其职**：

| 机制 | 适用 | 作用 |
|---|---|---|
| 悲观锁 `SELECT ... FOR UPDATE` | MySQL / PostgreSQL | 同一局的行被锁住，其他事务的读等待，天然串行；不重试、无冲突 |
| 乐观锁 `WHERE version = old` | 所有方言（SQLite 兜底） | 读到的快照过期就拒绝写入，绝不静默覆盖；冲突返回 409 |

SQLite 不支持 `FOR UPDATE`（SQLAlchemy 会忽略该子句），而且 SQLite 的写是整库串行的，
读锁升级写锁时可能直接 `database is locked`，所以**必须**叠加版本号 CAS：
否则「两个请求都读到 version=0，都写回 version=1」会丢更新。

为什么不用「悲观锁一把梭」：MySQL 行锁需要事务 + 索引命中，长事务会拖住连接池；
而 `version` 字段还顺带解决了「客户端拿旧快照回来写」的问题（可扩展成 If-Match / ETag）。
为什么不用「乐观锁一把梭」：高冲突场景重试成本高；生产 MySQL 上行锁让同一局的写天然排队，
体验更好。两者叠加 = 生产快、兜底稳。

内存实现则用 `asyncio.Lock` 保护临界区（单进程够用，跨进程无效），语义与 SQL 版本一致：
并发两次打同一张牌，只有一次成功。测试 `test_并发打同一局只有一次成功且状态不错乱`
在两种实现下都验证「牌河只多 1 张、总牌数守恒 136、当前玩家正确轮转」。

## 6. 未来扩展：Redis 缓存怎么加

当前 SQL 实现已经能扛住演示与单机生产，但热点对局每次都打库。下一步可以加 **cache-aside**：

1. **读**：`get(game_id)` 先 `GET game:{id}`，命中直接返回；未命中读库后 `SETEX`，
   TTL 取 `min(game_ttl_seconds, 300)`，比数据库的 TTL 短，避免缓存比库「活得更久」；
2. **写**：`discard` 在数据库事务**提交后**再 `DEL game:{id}`（先删缓存再改库会读到脏数据），
   或者用「写后更新 + 版本号比较」：只有新版本号大于缓存里的版本才覆盖；
3. **缓存击穿**：同一局是热点时用 `SETNX` 互斥回源，或本地 `asyncio.Lock` 按 game_id 分段；
4. **多实例一致性**：把 `version` 写进缓存值，写路径带 `version` 条件更新（Lua 脚本），
   避免「A 实例写库、B 实例删缓存」的竞态；
5. **Redis 也能当仓库**：`GameRepository` 再来一个 `RedisGameRepository`（`HSET` 存快照 +
   `WATCH/MULTI` 或 Lua 做 CAS），路由与测试完全复用——这正是接口优先的红利。

再往后（真实高并发）：对局状态机事件化（打牌写 `events` 表），用 Outbox 模式同步到缓存 /
消息队列，读写分离。当前项目规模不需要，写进 ADR 只为说明演进路径。

## 7. 后果与已知限制

**收益**

- 默认路径零依赖不变：121 个既有测试原样通过，新增 18 个持久化测试（共 139）；
- 换存储 = 改环境变量，路由/引擎/测试全部复用；
- 重启后对局可查（`test_应用重启后同一局仍可查询`）；
- 凭据安全：启动日志用 `mask_dsn` 把密码替换成 `***`。

**限制 / 下一步**

- 用 `create_all` 建表，没有 Alembic 迁移；改字段只能手工 `ALTER`，正式项目应接 Alembic；
- 每次读写都刷 `last_access`（`get` 也是一次 UPDATE），热点对局写放大，可用 Redis 承接读；
- `JSON` 列不做牌级索引，牌谱分析需另建事件表；
- SQLite 单文件写并发能力有限，仅用于本地验证；生产必须 MySQL/PostgreSQL；
- 连接池参数（`pool_size` / `max_overflow`）用默认值，生产要按 `workers × 并发` 调。

## 8. 面试可能追问（自测清单）

1. 为什么用抽象类而不是 Protocol / 直接 if-else？——依赖倒置、可注入假实现、开闭原则；
2. SQLite 没有行锁你怎么保证不丢更新？——事务 + `version` CAS，冲突 409；MySQL 下另有
   `FOR UPDATE`；
3. 为什么不用 `JSON` 拆表？——聚合根、读写局部性；代价与何时该拆事件表；
4. `get` 都写库会不会有性能问题？——会，所以有 Redis cache-aside 的演进方案；
5. 多实例部署时内存实现为什么不行？——`asyncio.Lock` 不跨进程，需 Redis 锁或库级锁；
6. 表结构怎么演进？——`create_all` 只适合初始化，长期用 Alembic；
7. 缓存与数据库不一致怎么办？——先写库后删缓存 + 版本号比较 + TTL 兜底；
8. 为什么关闭应用不 `DELETE FROM games`？——持久化的意义就是重启可恢复，清理交给 TTL/运维。
