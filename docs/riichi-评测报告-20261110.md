## 1. 方法

### 1.1 自对弈驱动（进程内，通用驱动）

```
game.NewWithOptions(seed, rules, {ManualResponses:true, ScoreProvider:RulesScorer})
loop 直到 PhaseGameEnd:
  AwaitDraw     → Apply(Legal()[0])                  # 摸牌；摸空=荒牌流局（引擎返回错误但状态已结算）
  AwaitDiscard  → agent.DecideWithTimeout(Observe(Turn), 500ms) → Apply
                  # 若合法动作里含自摸，驱动层强制取（能胡必胡）
  AwaitResponse → 对每个仍有 Responses 的座位问 agent（或按 --calls 策略取荣和/放弃）
  RoundEnd      → tallyRound(本局新增事件) → StartNextRound()
```

关键点：

1. **不假设动作种类**：只从 `Observation.LegalActions` / `Observation.Responses` 里选，
   吃碰杠立直和了全部走同一条 `Apply` 路径；引擎返回未实现动作错误时记录 `games[].error` 并跳过该场。
2. **决策超时**：`agent.DecideWithContext`，默认 500ms（契约 §4），超时回退启发式首选。
3. **和了必取**：S8 内置策略只输出「打牌」动作，不会主动叫和；评测层把「能胡必胡」
   作为统一规则补上（否则和了率会被策略实现细节掩盖）。
4. **可复现**：agent 的随机源由 `seed*4+seat` 派生，同 seed 同配置 → 同动作序列、同结果。

### 1.2 计分

默认注入 `eval.RulesScorer`（`game.Options.ScoreProvider` 的实现）：

- 把 `game.Meld` 转成 `rules.Meld` → `rules.Decompose(暗牌, 副露, 和了牌)` → `Evaluate`
  （役种/翻/符）→ 宝牌/赤宝牌/里宝牌加成 → `rules.Score` → 拆成四家净点数变化（总和为 0，
  本场计入，立直棒由引擎另加）；
- 门清、副露、暗杠、七对、国士都走真实规则（S5b commit `f37b275` 起 `Decompose` 支持副露）；
- 兜底：若引擎判和而 rules 拆不出/无役，回退 1 翻 30 符并在役种里标注「近似计分」。

### 1.3 指标与 ELO

| 指标 | 口径 |
|---|---|
| 和了率 / 放铳率 / 立直率 / 副露率 | 分子 / 该座位打过的轮数 |
| 平均顺位 | 每场半荘按最终点数排名（同分并列），再对场次取均值 |
| 平均打点 | 和了者收入（自摸为三家支付之和，含本场/立直棒）/ 和了次数 |
| 决策 P50/P95 | 单次 `Decide` 耗时（毫秒） |
| 役满数 | 和了事件 payload 里 `han >= 13` 的次数（含数え役满） |
| 置信区间 | 比例：正态近似 `p ± 1.96·√(p(1-p)/n)`；均值：样本方差标准误 |
| ELO | 半荘最终点数两两比较（同分各 0.5）→ Bradley-Terry `p_i/(p_i+p_j)`，MM 迭代上限 200 轮，最终平移到均值 1500 |

## 4. 解读

1. **排序可信**：`random` 在所有维度垫底（0.4% 和了率、19.1% 放铳率、平均顺位 3.70），
   与「随机合法动作」的预期一致；`shanten:attack` 在向听/进张上最强，和了率与平均顺位双第一，
   说明 S8 的「攻击打风」确实转化为实战胜率。
2. **`defense:defense` 的防守标签没有带来更低放铳率**（16.5% vs shanten 7.0%，甚至高于
   `search:closed` 14.8%）：它的打风权重偏向弃和/安全牌，但和了率低（22.2%）导致牌局更长、
   暴露在危险局面的回合更多；这是「打风参数 ≠ 绝对强度」的一个实据，也是下一步调参的入口。
3. **和了构成以荣和为主**（132 vs 49）：因为 S8 策略不主动立直、也很少自摸（`和了必取` 只在
   自摸时生效），对局形态更接近「门清推进 → 他家打危险牌 → 荣和」，这解释了立直率 0% 与
   荣和偏多。
4. **置信区间**：20 场下和了率 CI 仍约 ±5~6 个百分点（如 31.7% [25.7, 37.8]），
   足以区分 `random` 与其它三者，但不足以区分 `search:closed`(24.3%) 与
   `defense:defense`(22.2%)；要下更细的结论需要 ≥200 场。

## 5. 已知限制与原因（诚实口径）

1. **响应窗口默认 `pass`（只荣和）**：S5 的「吃/碰后打牌」流程尚未接通（鸣牌后
   `Legal()` 为空，`Apply` 无法推进），若让 agent 自由吃碰杠，对局会以 `aborted` 结束。
   因此评测默认禁鸣牌，保证 20 场全部跑完；等 S5 修好「鸣牌后打牌」后可用
   `--calls=agent` 打开真实副露博弈（代码路径已就绪，`CallsAgent` 分支已测）。
2. **立直率 ≈ 0**：S8 的 `shanten` / `defense` / `search` 目前只输出 `ActDiscard`，
   不会选 `ActRiichi`；只有 `random` 会误打误撞立直（0.4%）。评测层不代打立直，
   以免把「策略能力」和「驱动器补丁」混在一起。S8 支持立直后该指标自然激活。
3. **样本量**：20 场 / 230 轮；CI 较宽（见 §4.4）。默认 `--seeds 1-100` 可扩到 100 场；
   完整 1000 局出图属于里程碑 M5 的后续工作。
4. **计分兜底**：引擎判和但 rules 拆不出/无役时会回退 1 翻 30 符（事件 yaku 带「近似计分」）；
   本次 20 场未触发（`grep` 事件可查）。另外「无役和了」本应在引擎层拒绝，
   当前 S5 只判牌型不判役，属于引擎侧待补。
5. **未接入**：`Replay` 校验（用 `ReplayWithOptions` 逐 seed 复核动作序列）、
   store 落库、图表输出（目前 report.md 表格 + report.json 原始数据）。
6. **并发与复现**：结果只依赖 seed + agents 配置，与 `--jobs` 无关；
   已用「同 seed 两次运行 summary 完全一致」验证（去掉耗时字段后 DeepEqual）。

## 6. 复现

```bash
cd riichi

# 验收口径：20 场，输出到 .tmp-eval（已忽略提交）
go run ./cmd/riichi-eval --count 20 --out .tmp-eval

# 默认 100 场
go run ./cmd/riichi-eval --seeds 1-100

# 指定 4 个 agent（可用 agent.RegisteredNames() 里的任意组合）
go run ./cmd/riichi-eval --seeds 1-50 --agents shanten:attack,shanten:attack,defense:defense,search:closed

# 只打一局（快速 smoke）/ 调整并发
go run ./cmd/riichi-eval --count 20 --round-limit 1 --jobs 8

# 单测（含 100 局 smoke；-short 跳过 smoke）
go test ./internal/eval -count=1 -cover
```
