# riichi 规则引擎审计报告（2026-11-10）

> 目的：回答「规则引擎是否完全正确」。结论：**实现质量高、主流规则正确，但不是 100% 标准日麻**——
> 存在 5 个真实缺口（3 个可触发、2 个特殊流局未实现）与 3 处已在文档声明的刻意简化。
> 所有结论来自本仓库代码阅读 + 临时探针程序实测（探针已删除，用例见下文），不依赖「测试全绿」推断。

## 2. 真实缺口（会导致规则不正确）

### G1. 天和 / 地和永远不会触发（可触发场景，真缺口）
- 代码：`internal/game/score.go` 的 `WinContext.Tenhou/Chiihou` 注释为「预留」；
  `internal/game/flow.go:779 buildWinContext` **从未给这两个字段赋值**。
- 后果：庄家第一巡自摸、闲家第一巡（无鸣牌）自摸，都只算「门前清自摸和」，拿不到 13 翻役满。
- 规则层本身是对的：探针把 `ctx.Tenhou=true` 传进去，`Evaluate` 能正确返回「天和 13 翻」。
- 修法：`buildWinContext` 里按「本局无人副露 && 摸牌次数≤1（庄）/ 首巡」置位；或由 `flow.go` 在和了判定处传标记。

### G2. 三家和了被当成「三家都荣和」结算（真缺口）
- 代码：`flow.go` `resolveResponses → ronWinners → settleRons`；`settleRons` 对**每个** winner 逐个 `applyDeltas`。
- 默认 `Ruleset.DoubleRon=true`（双响允许，与天凤一致）；但三家同时荣和时，三家都会被结算、放铳者被扣三次。
- 天凤规则：**三家和了 = 途中流局**（不结算、亲家连庄）。
- 修法：`resolveResponses` 里 `len(winners) >= 3` 直接 `finishRyuukyoku(三家和了, abortive=true)`。
- 现有测试只覆盖双响/头跳，**没有三家和用例**（这是漏测点）。

### G3. 双倍役满未实现（可触发，规则偏差）
- 代码：`yaku.go` `yakumanHan = 13`，每个役满固定 13 翻；注释说「天凤默认单倍」。
- 实测：国士十三面 = 13 翻 32000（天凤应为 **双倍役满 64000**）；四暗刻单骑 = 13（应双倍）；
  大四喜 = 13（应双倍）；纯正九莲 = 13（应双倍）。
- 叠算实测：大四喜 + 字一色 + 四暗刻 = 39 翻 / **96000**（天凤：大四喜双倍 + 字一色 + 四暗刻 = 4 倍役满 **128000**）。
- 修法：`Yaku` 增加 `YakumanMultiplier int`（1 或 2），`evalYakuman` 按待ち/牌型置 2；`han = 13 × multiplier`。

### G4. 流し満貫 未实现（特殊流局，低频）
- 代码：`flow.go:134` 注释「RyuukyokuNagashi 是流し満貫（规则开关，暂未实现）」，无判定逻辑。
- 影响：荒牌流局时不会结算流し満貫。

### G5. 四家立直 途中流局 未实现（特殊流局，极低频）
- 代码中无四家立直判定；四家都立直后会一直打到荒牌流局。
- 天凤：四家立直 → 途中流局。

## 3. 刻意简化（已声明，但严格说不符合标准）

| 简化点 | 代码位置 | 标准规则 | 影响 |
|---|---|---|---|
| 立直后禁止暗杠/加杠 | `flow.go:349/377`「简化规则」 | 暗杠若**不改变听牌**是允许的（天凤允许） | 立直后少一种合法操作（偏保守，不会算错点） |
| 食替禁则范围 | `flow.go` 同种 + 筋±3 | 常见规则只禁「同种」；部分规则允许食替 | **偏严格**：会禁止部分合法打牌（影响可玩性，不影响计分正确性） |
| 役满单倍 | 同 G3 | 天凤对国士十三面/四暗刻单骑/大四喜/纯正九莲双倍 | 高打点手少 50% |

## 4. 审计结论

- **主流规则（符、役、点数、振听、立直、副露、响応窗口、流局听牌料、连庄、本场/立直棒、宝牌/赤/裏）实现正确**，探针逐项验证通过；
- 规则引擎的**测试覆盖扎实**（rules 96.2%、29 手金标 + v1 回归 39/39 + 副露 69 个子测试），但**测试没覆盖到 G1/G1/G3 这类「特殊和了/流局」路径**——这正是「全绿 ≠ 全对」的地方；
- 若要对外宣称「完整天凤规则」，需要补 G1–G5；若定位为「主流日麻规则引擎（部分特殊流局从简）」，则只需在 README/讲法里把 G1/G2/G3 明确写成已知限制（目前已写 G3 的一部分：单倍役满）。

## 5. 建议修复顺序

1. **G2 三家和**（半小时，漏测点 + 结算错误，最容易在面试被问）；
2. **G1 天和/地**（1 小时，`buildWinContext` 置位 + 2 个测试）；
3. **G3 双倍役满**（1-2 小时，加 multiplier 字段 + 改金标期望）；
4. **G4/G5 特殊流局**（各 1-2 小时，低频，可后置）；
5. 食替禁则改为可配（`Ruleset.Kuikae` 枚举）——影响可玩性，建议做。
